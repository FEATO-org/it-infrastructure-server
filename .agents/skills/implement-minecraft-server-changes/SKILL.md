# Implement Minecraft server changes

## When to use

ChatGPTなどで決めた要件・実装計画・修正方針を、Minecraftサーバー関連リポジトリへ反映するときに使う。設計をやり直さず、計画の不足分だけ既存実装から確認する。

## Workflow

1. ルートから対象ディレクトリまでの `AGENTS.md` を読み、このSkillより優先する。変更記録の規則があれば `changes/README.md` も読む。
2. 計画と対象範囲を確認する。修正対象、近接する実装、使用中のAPI・ライブラリ、設定方式、関連するテスト・ビルド方法だけ調べる。計画で確定した内容を再調査しない。
3. 既存の構成と運用上の読み込み先を踏まえ、必要なファイルを実装する。計画と現状が矛盾する場合は根拠を確認し、外部仕様を変える解釈が必要なら確認する。
4. 指定された検証と、変更のリスクに見合う検証を行う。結果を確認する。
5. 利用者への影響を判定し、必要なら `changes/pending/` に変更記録を追加する。
6. 最終差分、未追跡・ステージ済みファイル、意図しない変更や秘密情報の混入を確認して報告する。

## Implementation rules

- 既存アーキテクチャ、命名、コードスタイル、エラー処理、設定方式を守る。最小限の変更で可読性と保守性を優先する。
- 不要な抽象化、読みにくいメタプログラミング、指示されていない広範なリファクタリング、コードから明らかなコメントを加えない。既存仕様やセキュリティ境界を不用意に変えない。
- 値を固定すべきでない場合は既存の設定方法を使う。必要なら既存テストを更新する。
- Minecraftの設定やインフラでは、Git管理の配布元、永続データ、実行時の読み込み先を区別する。適用・デプロイ・実サーバー操作は依頼範囲と権限を確認し、静的検証を本番確認と呼ばない。
- 秘密鍵、token、`.env`、プレイヤーデータ、DBやWorldのバックアップを変更記録・差分・報告に含めない。

## User clarification rules

既存仕様と計画から合理的に決められる実装詳細は自律的に決める。次は推測せず、判明している部分の作業を進めながらユーザーに確認する。

- 利用者から見て何が変わるか、または利用者影響の有無を確定できない。
- 解釈によって外部仕様が変わる。
- 必要な変更理由が確定できない、または複数の合理的な理由がある。
- `category` や `scope` をリポジトリ規則と既存例から確定できない。

技術的な実装事情をユーザーの意図した変更理由として書かない。純粋な新機能・コンテンツ追加や単純な不具合修正など、理由の説明が不要なら確認せず `reason` を省く。

## User-facing change detection

実装後、ファイル種別ではなく最終的な利用者体験で判定する。新機能・コンテンツ、仕様やバランス、アイテムやMobの挙動、権限・利用条件、メッセージ・UI・表示、設定による体験、不具合修正は原則として記録する。内部リファクタリング、整形、コメント、テスト、CI/CD、開発環境、内部ログ、外部挙動が変わらない依存関係整理・内部実装置換だけなら記録しない。境界事例は `AGENTS.md` と `changes/README.md` に従い、具体的な変更事実を確認できないまま記録を作らない。

## Change file generation

利用者影響があれば、作業完了前に `changes/pending/<descriptive-name>.md` を追加する。短い識別可能な kebab-case を使い、原則として利用者にとって独立した変更ごとに1ファイルとする。まずリポジトリ固有の形式・許容値を使う。規則がなければ `category` は `feature`（新機能）、`content`（新コンテンツ）、`balance`（バランス）、`improvement`（改善）、`fix`（不具合修正）、`system`（システム変更）、`breaking`（重要な互換性・仕様変更）から選ぶ。`scope` は対象の安定した識別子とし、既存値があれば再利用する。

```yaml
---
category: improvement
scope: ancient-coin
change: 古銭にエンチャント光沢を常時表示するようにしました。
reason: 通常の金塊系アイテムと見分けにくかったためです。
---
```

`change` は必須。利用者から観測できる具体的な変更事実を原則1文で書く。「見分けやすくしました」「改善しました」などの効果や目的だけで済ませない。`reason` は必要な場合だけ、確認できた変更理由を別の1文で書く。どちらも簡潔な利用者向けの言葉にし、内部のクラス名など不要な技術詳細、推測、誇張、将来予定、Markdown見出し、絵文字、完成版パッチノートの体裁を含めない。

## Validation

ユーザーが「テスト不要、ビルドのみ」など検証条件を指定した場合はそれを優先する。それ以外は既存のテスト・ビルド方法と変更リスクに応じて確認する。シェルやComposeなどには該当する構文・設定検証を適用し、秘密値を展開した出力を共有しない。`git diff --check` と対象の差分を確認する。本番動作が未確認ならそのまま報告する。

## Completion criteria

- 計画された実装が完了し、不要な変更がない。
- 指定された検証を実施し、結果を確認した。
- 利用者影響を判定し、必要な変更記録を追加した。`change` は具体的事実であり、`reason` は必要な場合だけ根拠に基づいている。
- 不明な意図や理由を補作していない。最終差分に意図しない変更や秘密情報がない。

完了報告は、実装内容、主な変更ファイル、検証と結果、追加した変更記録、未解決事項のみを簡潔に示す。利用者影響なしと判断して記録しなかった場合はその旨を明記する。
